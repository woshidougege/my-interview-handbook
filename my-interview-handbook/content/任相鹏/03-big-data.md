## Flink 实时计算

### [[Flink|夫林克|Apache Flink 实时流式计算引擎]]

**核心特点**

- **流批一体**：同一套代码处理流数据和批数据
- **低延迟**：毫秒级延迟，比 Spark Streaming 快
- **高吞吐**：单机百万 QPS
- **Exactly-Once**：数据不重不丢

**核心概念**

- **[[Checkpoint|切克破因特|状态快照机制]]**：故障恢复的基础
- **[[Watermark|沃特马克|处理乱序数据的时间戳机制]]**：处理乱序数据
- **状态管理**：TB 级状态数据（RocksDB）
- **反压**：下游慢了自动降速

### Flink vs Spark

| 特性 | Flink | Spark Streaming |
|------|-------|-----------------|
| 计算模型 | 真流处理 | 微批处理 |
| 延迟 | 毫秒级 | 秒级 |
| 状态管理 | 强 | 弱 |
| 生态 | 发展中 | 成熟 |

## Kafka 消息队列

### [[Kafka|卡夫卡|分布式消息队列]]

{KafkaArchitecture}

**核心功能**

- 消息队列：生产者发消息，消费者订阅
- 流处理：实时处理数据流
- 高吞吐：百万级 QPS
- 持久化：消息存储在磁盘

**核心概念**

- **Topic**：消息主题，类似数据库的表
- **Partition**：分区，提升并行度
- **Offset**：消息位置，消费进度
- **Consumer Group**：消费者组，负载均衡

## Hudi 数据湖

### [[Hudi|呼嘀|Apache Hudi 流式数据湖]]

{HudiArchitecture}

**核心功能**

- 流批一体：实时写入 + 批量查询
- ACID 事务：保证数据一致性
- 增量消费：只读变更数据
- 时间旅行：查询历史版本

### 两种表类型

**COW（Copy On Write）**
- 写时复制
- 查询快，写入慢
- 适合实时增量场景

**MOR（Merge On Read）**
- 读时合并
- 写入快，查询慢
- 适合 CDC 同步

## Checkpoint 机制

### 为什么需要 [[Checkpoint|切克破因特|状态快照]]？

- 故障恢复：任务挂了从 Checkpoint 恢复
- 数据不丢不重：Exactly-Once 语义
- 状态管理：TB 级状态数据持久化

### 工作原理

1. JobManager 触发 Checkpoint
2. 向 Source 插入 Barrier 标记
3. Barrier 随数据流向下游传递
4. 每个算子保存状态快照
5. 上传到 HDFS/S3 等存储
6. 全部完成后标记为成功

### 配置要点

- 间隔时间：5-10 分钟（太频繁影响性能）
- 超时时间：10 分钟（避免长时间阻塞）
- 最大并发：1-2 个（避免资源竞争）
- 状态后端：RocksDB（大状态场景）

## HDFS 分布式存储

### [[HDFS|H-D-F-S|Hadoop 分布式文件系统]]

**特点**

- 高容错：数据自动复制（默认 3 副本）
- 高吞吐：适合大文件批量读写
- 可扩展：支持 PB 级数据
- 一次写入多次读取

**架构**

- **NameNode**：元数据管理（文件目录树）
- **DataNode**：数据存储（实际数据块）
- **SecondaryNameNode**：元数据备份

## 性能优化实践

### Kafka 优化

1. **分区数优化**：256 分区，提升并行度
2. **批量发送**：batch.size = 16KB
3. **压缩**：lz4 压缩，减少网络传输
4. **异步发送**：提升吞吐量

### Flink 优化

1. **算子链优化**：合并算子，减少序列化
2. **异步 IO**：数据库查询异步化
3. **Checkpoint 调优**：间隔 5-10 分钟
4. **状态后端**：RocksDB 增量 Checkpoint

## 面试高频问题

### Q1：Flink 如何保证 Exactly-Once？

通过 Checkpoint + 两阶段提交实现：

1. Checkpoint 保存状态快照
2. 外部系统支持事务（如 Kafka 事务）
3. 两阶段提交：预提交 + 正式提交

### Q2：Kafka 如何保证消息不丢失？

1. **生产者**：acks=all（等待所有副本确认）
2. **Broker**：min.insync.replicas=2（至少 2 个副本）
3. **消费者**：手动提交 offset

### Q3：Flink 反压怎么处理？

反压是下游处理慢，数据堆积：

1. **增加并行度**：提升处理能力
2. **优化算子**：减少计算量
3. **异步 IO**：数据库查询异步化
4. **扩容资源**：增加 CPU/内存
